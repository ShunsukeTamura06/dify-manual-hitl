# 大規模文書スプリッター 設計メモ（R&D 結果）

## 解きたい問題
現場には「1ファイルに大量の情報を集約した文書」（例: 80ページの金融検査マニュアル別冊）がある。
これを **適切な単位で複数ページに分割** して一元化環境に整理したい。
現状の登録 Bot は「1ファイル=1ページ」設計のため、大きな文書を1ページに**要約**してしまう
（実測: 抽出 59,350字 → 整形 LLM 出力 5,143字 = 98% が脱落。原因は max_tokens 上限 +
1ページ設計）。

## 実データ R&D で分かったこと（金融検査マニュアル別冊で検証）

1. **抽出は正常**。テキストは約 59K 字（330K は JSON エスケープで膨張した見かけ）。
   gpt-4o-mini の文脈には収まる。問題は **出力**（1回の LLM 出力に全部は入らない）。
2. **正規表現での見出し分割は過剰分割**。各事例内の「1. 2. 3.」まで切ってしまい 116 個に
   （「適切な単位」は正規表現では決められない）。
3. **LLM のアウトライン生成は優秀**。文書全体を渡すと、意味単位（はじめに / 検証ポイント /
   事例1〜28）を正しく 31 ページに分けた。**ページ単位の判断は LLM が得意**。
4. **アンカー（開始位置）の特定が難所**。
   - LLM はタイトルを言い換えるため「逐語アンカー」は実在せず exact 一致は 2/31。
   - 正規化（全角→半角・記号除去）ファジー一致は 31/31 当たるが、**目次(TOC)の
     「事例N」を拾ってしまう**（目次と本文で同じ語が2回出る）。
   - 本文には「（事例N）」という明確なマーカーが実在するが、「本事例の場合」等の
     参照（84回）と区別が要る。

→ 結論: **LLM の構造理解は使える。決定的な「切り出し」を堅牢にするのが本質的な作業。**

## 推奨アーキテクチャ（2案）

### 案A: チャンク Map-Reduce（堅牢・汎用。アンカー不要）
1. 本文を段落境界で ~6-8K 字のウィンドウに機械分割（Code）。
2. 各ウィンドウを LLM で処理 → そのウィンドウ内の **完結したトピックページ** を
   JSON 配列で出力（continues_previous / incomplete フラグ付き）。
3. Reduce: ウィンドウ跨ぎのセクションを継ぎ合わせ → 各ページを GROWI に作成。
- 利点: アンカー特定が不要。内容を落とさない。文書構造に依存しない。
- 欠点: LLM 呼び出しが増える（この文書で6-8回）。継ぎ合わせロジックが必要。

### 案B: LLM アウトライン + マーカー切り出し
1. LLM が全文からアウトライン（順序付きの {title, type}）を生成。
2. TOC を除外し、本文の繰り返しマーカー（最頻の見出しパターンを自動検出）で切り出し。
3. アウトラインとセクションを順序で対応付け → 各ページを整形・作成。
- 利点: LLM 呼び出しが少ない。
- 欠点: マーカー検出が文書依存で脆い（TOC 重複・参照ノイズ・表記揺れ）。

→ **汎用性・堅牢性で案A（Map-Reduce）を推奨。**

## Dify 実装スケッチ（案A）
```
ファイル抽出 → TOC除去/前処理(Code) → ウィンドウ分割(Code, 配列出力)
  → Iteration ノード（各ウィンドウ）:
       LLM(このウィンドウの完結ページを抽出・整形, フラグ付き)
  → 継ぎ合わせ(Code: incomplete↔continues_previous をマージ)
  → Iteration ノード（各ページ）:
       項目抽出(path/title) → upsert(作成)
  → 回答: 「N ページを作成しました」一覧
```
- 既存の登録 Bot（1ページ）とは別フロー（別アプリ「一括取り込みBot」）にするのが素直。
  単一ページの新規/更新マージは現行 Bot、巨大文書の分割取り込みはこの新 Bot。
