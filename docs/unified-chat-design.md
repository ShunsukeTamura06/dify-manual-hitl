# 統一チャット設計メモ（4アプリ → 1入口・LLM意図分類 + 決定的サニタイズ）

## 解きたい問題

現状、ユーザー向けの入口が 4 アプリ（質問 / 登録 / 一括取り込み / 重複排除）に分かれており、
**どの Bot を使うかの判断がユーザーに委ねられている**。特に登録と一括取り込みの選択を
誤ると、大きな文書が 1 ページに要約されて内容が大幅に欠落する（実測 98% 欠落。
[splitter-design.md](splitter-design.md) の起点となったバグと同じ状況）。

→ **1 つのチャット入口**に統合し、bot が意図を汲んで裏で適切なフローに振り分ける。
ユーザーはどの機能かを選ばず「ファイルを投げる／質問する／整理を頼む」だけでよい。

## スコープ（完全 bot: 4 機能すべて統合）

| 対象 | 統合 | 備考 |
|------|------|------|
| 質問 Bot | ✅ 統合 | 全社員・毎日使うメイン動線 |
| 登録 Bot | ✅ 統合 | 整備者。登録/一括の選択ミスが実害最大 |
| 一括取り込み Bot | ✅ 統合 | 同上 |
| 重複排除 Bot | ✅ 統合 | 「重複を整理して」で起動。**現状は提示まで**（統合の実行は未実装） |

## ルーティング方式: LLM 意図分類 + 決定的サニタイズ

「自律的に振り分ける」ため、意図の判断は LLM に委ねる。ただし LLM の誤分類が
**書込系フローの誤発火**にならないよう、確実に判定できる物理的事実（添付の有無・
抽出文字数）で LLM の結果を必ず矯正する。役割分担:

- **ルーターLLM**: ユーザーのメッセージから意図を qa/register/bulk/dedup に分類（自律判断）。
- **ルーター Code（決定的サニタイズ）**: LLM の分類を採用しつつ、添付・サイズ・明示
  キーワードで最終決定する。これが安全弁。単体テストでローカル完結（stdlib のみ）。

### ルーティング規則（決定的サニタイズの優先順位順）

| # | 条件 | ルート | 根拠 |
|---|------|--------|------|
| 1 | 添付なし + 「重複」等 or LLM意図=dedup | **dedup** | 書込材料が無い＝質問か重複整理のみ。LLM 意図を採用 |
| 2 | 添付なし（上記以外） | **qa** | LLM が書込系を出しても qa に矯正（誤発火の遮断） |
| 3 | 添付あり + 「分割」or「一括」 | **bulk** | 明示指示は最優先 |
| 4 | 添付あり + 「更新」 | **register** | 既存ページへのマージ経路 |
| 5 | 添付あり + 抽出テキスト > 7,000 字 | **bulk** | スプリッターのウィンドウ上限。分割しないと欠落する |
| 6 | 添付あり + LLM意図=bulk | **bulk** | 決定打が無ければ LLM の bulk 提案を尊重 |
| 7 | 添付あり（上記以外） | **register** | 1 ファイル 1 ページの通常登録。dedup/qa 意図も register に矯正 |

- 閾値 7,000 字は一括取り込み側の `DEFAULT_MAX_CHARS` と同じ定数（1 回の LLM 出力に
  無理なく収まる量を超えたら分割が必要）。
- **添付の有無が最上位の安全弁**: 添付が無ければ register/bulk は物理的に選べない
  （LLM がそう言っても qa/dedup に矯正）。添付があれば dedup/qa は register に倒す。
- 複数ファイル添付は抽出テキストの合計長で判定。判定は決定的比較でテスト可能。

**曖昧な指示の倒し方（規則の優先順位の根拠）**:
- 規則 2 > 3（「分割して更新して」→ bulk）: 誤 bulk は**新規 draft が増えるだけ**で
  人が捨てられる。誤 register(更新) は**既存ページ本文を書き換える**（履歴で戻せるが
  影響が大きい）。迷ったら影響の小さい方に倒す。
- 規則 3 > 4（大きい更新素材 → register）: bulk は既存ページを更新できない（新規作成のみ）
  ため「更新」の明示指示を尊重する。

### 誤ルートの安全網

ルーティングを誤っても壊れない設計にする（fault isolation）:

- register / bulk とも書き込みは **draft**（検索に出ない）。誤発火しても人が GROWI で
  気づいて捨てられる。
- qa への誤ルート（本当は登録したかった）は何も書き込まないので無害。
  「登録したい場合はファイルを添付してください」と案内を返す。
- IF/ELSE の **既定（ELSE）は書込系に向けない**。qa / register / bulk すべて明示 case とし、
  ルーター出力が想定外（空・将来の値追加）のときは案内文を返すだけのフォールバックに落とす。

### v1 の既知の制約（v2 課題）

- **添付ファイルへの質問はできない**: 添付＝取り込み意図とみなす（開始メッセージで案内）。
  「この PDF について教えて」のような添付付き質問は register に流れ、draft が 1 つ
  作られる（無害だが意図と違う）。添付内容への QA は v2 の機能課題。
- **巨大な更新素材**: 「更新」指示は register のマージ経路に流れるが、マージ LLM の
  出力上限を超える素材では内容が欠落し得る。bulk 側に更新（既存ページへの分割マージ）
  機能が無いため、v1 では受け付けたうえで人が draft 段階で確認する運用とする。

## どこで何が動くか（責務分離）

```
[Start] → [Document Extractor(sys.files)] → [ルーターLLM(意図分類)]
   → [ルーター(Code・決定的サニタイズ)] → [IF/ELSE 4分岐]
   ├─ qa:       Knowledge Retrieval → 回答LLM → Answer（既存 質問Bot と同一）
   ├─ register: 整形LLM → 類似検索 → 更新判定 → get-content → マージLLM
   │            → upsertボディ組立 → POST /pages/upsert → Answer（既存 登録Bot と同一）
   ├─ bulk:     ウィンドウ分割(Code) → Iteration(抽出LLM) → 継ぎ合わせ(Code)
   │            → Iteration(upsert) → Answer（既存 一括取り込みBot と同一）
   └─ dedup:    対象範囲(Code) → 一覧取得 → Iteration(本文取得) → 提案組立(Code)
                → 整形 → Answer（既存 重複排除Bot と同一。提示まで）
   （ELSE: ルーター出力が想定外のときは案内文のみのフォールバック。書き込まない）
```

| 工程 | 実体 | 備考 |
|------|------|------|
| 意図分類 | **ルーターLLM ノード** | メッセージから qa/register/bulk/dedup を提案（自律判断） |
| 最終決定 | **Code ノード（純粋ロジック）** = 本リポジトリ `dify/unified-chat/` | stdlib のみ。添付・サイズで LLM を矯正。単体テストはローカル完結 |
| 分岐 | Dify IF/ELSE ノード | ルーターの `route` 出力で 4 分岐（+ELSE フォールバック） |
| 各フロー | 既存 4 Bot の検証済みノード群をそのまま移植 | **中身のロジック・プロンプトは変更しない**（実機検証済みの資産を保全） |

## 設計原則チェックリスト（design-principles.md）

- [x] 責任は 1 つか → 「ユーザー入力を適切なフローへ振り分けて実行する」。統合されるのは
      **入口だけ**で、各フローの責務は従来どおり
- [x] 他のアプリを直接呼んでいないか → Knowledge / DocStore Adapter 経由のみ（従来と同じ）
- [x] 設定は環境変数か → DOCSTORE_URL / DOCSTORE_API_KEY / dataset_ids（従来と同じ）
- [x] Wiki 実装に依存していないか → Adapter 越し（従来と同じ）
- [x] LLM プロバイダ非依存か → モデルはノード設定で差し替え可能（従来と同じ）
- [x] 単独で起動・停止できるか → 1 つの Dify アプリ。既存 3 アプリは移行期間中併存できる
- [x] 契約はドキュメント化されているか → 本ドキュメント + docstore-openapi.yaml
- [x] 失敗時に他を巻き込まないか → 誤ルートの書込は draft 止まり（上記の安全網）

## 既存 3 アプリの扱い（移行）

- v1 検証中は併存（統一チャットと個別 Bot のどちらも動く。同じ Adapter / Knowledge を
  共有するだけで相互依存はない）。
- 統一チャットが安定したら、個別の質問/登録/一括アプリは退役してよい。
  重複排除 Bot は管理者用として残す。

## DSL の組み立て方針

- 既存 4 Bot の**実機検証済み DSL** からノード・エッジをスクリプトで機械的に合成する
  （ノード ID を名前空間化し、value_selector / iteration_id 等の参照を一括で再配線）。
  手作業のコピペで参照を壊すより安全で、再現可能。参照切れは生成時に自動検証する。
- 合成後の DSL をローカル Dify にインポートし、4 ルートすべてを実機で一気通貫検証
  してからコミットする（このリポジトリの通例）。

## 検証方針

1. ルーターコア: 決定的サニタイズの規則と境界（添付有無での書込遮断・LLM 意図の矯正・
   ちょうど 7,000 字・キーワード複合・空クエリ・複数ファイル）を単体テスト。
2. 実機 E2E: 4 ルートが自律ルーティングで正しく振り分くこと。
3. いずれのルートでも sync の draft 除外（HITL ゲート）が保たれること。
