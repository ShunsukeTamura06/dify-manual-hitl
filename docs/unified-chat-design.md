# 統一チャット v1 設計メモ（4アプリ → 1入口・決定的ルーティング）

## 解きたい問題

現状、ユーザー向けの入口が 4 アプリ（質問 / 登録 / 一括取り込み / 重複排除）に分かれており、
**どの Bot を使うかの判断がユーザーに委ねられている**。特に登録と一括取り込みの選択を
誤ると、大きな文書が 1 ページに要約されて内容が大幅に欠落する（実測 98% 欠落。
[splitter-design.md](splitter-design.md) の起点となったバグと同じ状況）。

→ **1 つのチャット入口**に統合し、裏で適切なフローに振り分ける。
ユーザーは「ファイルを投げる or 質問する」だけでよい。

## スコープ（v1）

| 対象 | 統合 | 理由 |
|------|------|------|
| 質問 Bot | ✅ 統合 | 全社員・毎日使うメイン動線 |
| 登録 Bot | ✅ 統合 | 整備者。登録/一括の選択ミスが実害最大 |
| 一括取り込み Bot | ✅ 統合 | 同上 |
| 重複排除 Bot | ❌ 別アプリのまま | 保守担当者専用・利用頻度が低い・誤発火のリスク（書込系の一括操作）を入口に混ぜない |

## ルーティング方式: v1 は決定的（LLM 判断にしない）

振り分けを誤ると書込系フローが誤発火するため、v1 は**確実に判定できる材料**
（添付の有無・抽出文字数・明示キーワード）だけで分岐する。LLM による意図分類
（question-classifier ノード等）は誤分類コストが高いので v2 以降の検討事項。

### ルーティング規則（優先順位順）

| # | 条件 | ルート | 根拠 |
|---|------|--------|------|
| 1 | 添付なし | **qa**（質問応答） | 書込材料が無い以上、書込フローはあり得ない |
| 2 | 添付あり + メッセージに「分割」or「一括」 | **bulk** | 明示指示は最優先（サイズ規則の誤りを人が上書きできる） |
| 3 | 添付あり + メッセージに「更新」 | **register** | 既存ページへのマージは登録フローの更新経路が担当 |
| 4 | 添付あり + 抽出テキスト > 7,000 字 | **bulk** | 7,000 字 = スプリッターのウィンドウ上限（[splitter-design.md]）。1 回の LLM 出力に収まらない量は分割しないと欠落する |
| 5 | 添付あり（上記以外） | **register** | 1 ファイル 1 ページの通常登録 |

- 閾値 7,000 字は一括取り込み側の `DEFAULT_MAX_CHARS` と同じ定数を使う（意味: 「1 ウィンドウ
  ＝1 回の LLM 出力に無理なく収まる量」を超えたら分割が必要）。
- 複数ファイル添付は抽出テキストの合計長で判定する。
- 判定はすべて文字列・数値の決定的比較。単体テストでローカル完結できる。

### 誤ルートの安全網

ルーティングを誤っても壊れない設計にする（fault isolation）:

- register / bulk とも書き込みは **draft**（検索に出ない）。誤発火しても人が GROWI で
  気づいて捨てられる。
- qa への誤ルート（本当は登録したかった）は何も書き込まないので無害。
  「登録したい場合はファイルを添付してください」と案内を返す。

## どこで何が動くか（責務分離）

```
[Start] → [Document Extractor(sys.files)] → [ルーター(Code・決定的)] → [IF/ELSE]
   ├─ qa:       Knowledge Retrieval → 回答LLM → Answer（既存 質問Bot と同一）
   ├─ register: 整形LLM → 類似検索 → 更新判定 → get-content → マージLLM
   │            → upsertボディ組立 → POST /pages/upsert → Answer（既存 登録Bot と同一）
   └─ bulk:     ウィンドウ分割(Code) → Iteration(抽出LLM) → 継ぎ合わせ(Code)
                → Iteration(upsert) → Answer（既存 一括取り込みBot と同一）
```

| 工程 | 実体 | 備考 |
|------|------|------|
| ルーター | **Code ノード（純粋ロジック）** = 本リポジトリ `dify/unified-chat/` | stdlib のみ。`main()` を貼り付け可能。単体テストはローカル完結 |
| 分岐 | Dify IF/ELSE ノード | ルーターの `route` 出力で 3 分岐 |
| 各フロー | 既存 3 Bot の検証済みノード群をそのまま移植 | **中身のロジック・プロンプトは変更しない**（実機検証済みの資産を保全） |

## 設計原則チェックリスト（design-principles.md）

- [x] 責任は 1 つか → 「ユーザー入力を適切なフローへ振り分けて実行する」。統合されるのは
      **入口だけ**で、各フローの責務は従来どおり
- [x] 他のアプリを直接呼んでいないか → Knowledge / DocStore Adapter 経由のみ（従来と同じ）
- [x] 設定は環境変数か → DOCSTORE_URL / DOCSTORE_API_KEY / dataset_ids（従来と同じ）
- [x] Wiki 実装に依存していないか → Adapter 越し（従来と同じ）
- [x] LLM プロバイダ非依存か → モデルはノード設定で差し替え可能（従来と同じ）
- [x] 単独で起動・停止できるか → 1 つの Dify アプリ。既存 3 アプリは移行期間中併存できる
- [x] 契約はドキュメント化されているか → 本ドキュメント + docstore-openapi.yaml
- [x] 失敗時に他を巻き込まないか → 誤ルートの書込は draft 止まり（上記の安全網）

## 既存 3 アプリの扱い（移行）

- v1 検証中は併存（統一チャットと個別 Bot のどちらも動く。同じ Adapter / Knowledge を
  共有するだけで相互依存はない）。
- 統一チャットが安定したら、個別の質問/登録/一括アプリは退役してよい。
  重複排除 Bot は管理者用として残す。

## DSL の組み立て方針

- 既存 3 Bot の**実機検証済み DSL** からノード・エッジをスクリプトで機械的に合成する
  （ノード ID を名前空間化し、value_selector / iteration_id 等の参照を一括で再配線）。
  手作業のコピペで参照を壊すより安全で、再現可能。
- 合成後の DSL をローカル Dify にインポートし、3 ルートすべてを実機で一気通貫検証
  してからコミットする（このリポジトリの通例）。

## 検証方針

1. ルーターコア: 規則 1〜5 と境界（ちょうど 7,000 字・キーワード複合・空クエリ・
   複数ファイル）を単体テスト。
2. 実機 E2E:
   - 添付なしで質問 → 出典付き回答（qa）
   - 小さいファイル添付 → 1 ページ draft 作成（register）
   - 小さいファイル + 「更新して」 → 既存ページマージ・status 維持（register 更新経路）
   - 大きいファイル（>7,000 字）添付 → 複数ページ draft 作成（bulk）
   - 小さいファイル + 「分割して」 → bulk への明示上書き
3. いずれのルートでも sync の draft 除外（HITL ゲート）が保たれること。
