# 重複排除 提案フロー 設計メモ（HITL: 提案→承認→実行）

## 解きたい問題
カオスなマニュアル群を取り込むと、同じ事実が複数ページに散らばる（重複）。
最終目標「過不足ない wiki」のためには重複を 1 事実 1 ページに収束させる必要がある。
ただしこのプロジェクトの HITL は **「提案 → 承認 → 実行」**（人は編集作業者でなく承認者）。
→ 既存の「重複は提示のみ／読み込み時に透明化」（[architecture.md](architecture.md)）から一歩進め、
**書き込み時に統合案を出して承認を取ってから統合する**中間解を実装する。
（人手維持を強制しない現場方針は維持。ハードな承認ブロックではなく「提案＋承認」。）

位置づけ: [design-principles.md](design-principles.md) の「保守 Workflow（重複・古さ・孤立を
検知して通知）」を、**通知でなく提案→承認→実行**へ発展させたもの。登録/一括取り込み Bot
（書込）とは別アプリ（保守系）。アプリ間は直接呼ばず Adapter / Knowledge 経由（ルール 1）。

## フロー全体（図は会話の proposal_engine 図に対応）

```
① コーパス解析   : Wiki の全ページを走査し、類似ページの候補ペアを得てクラスタ化
② 提案生成       : 各クラスタに統合案（基準ページ・確信度・差分統計）を組み立てる
③ 差分提示       : ビフォー/アフター・保持/削除・矛盾点を人に見せる
④ 承認           : 高確信は一括承認、曖昧・矛盾ありは個別承認（承認負荷の設計）
⑤ 実行           : LLM が統合本文を生成 → 統合ページを upsert、重複ページを退役
```

## どこで何が動くか（責務分離）

| 工程 | 実体 | 文書非依存性 |
|------|------|--------------|
| 候補ペア取得（意味的類似） | **Dify Knowledge Retrieval**（各ページを問い合わせ、top-k 類似＋score）。登録 Bot の「類似ページ検索」を再利用 | 埋め込みベースなので依存なし |
| クラスタ化・確信度・提案組立 | **Code ノード（純粋ロジック）**＝本リポジトリ `dify/dedup/`。union-find ＋ difflib の重なり統計 | 完全に文書非依存（マーカー非依存） |
| 差分・矛盾の可視化／統合本文生成 | **LLM ノード**（承認後に統合本文を生成。事実は保持、重複は 1 つに、矛盾は注記＋採用理由） | プロンプトはドメイン用語非依存 |
| 統合の確定（作成・退役） | **HTTP（DocStore Adapter）** | Wiki 実装非依存 |
| 承認 | **チャットの対話ターン**（conversation 変数に提案状態を保持） | — |

→ **このリポジトリで先に固める＝決定的なコア（クラスタリング＋提案組立）**。ローカルで
単体テスト完結。意味検索（候補ペア）と統合本文生成（LLM）は Dify 側で、本コアはその
結果を決定的に処理する（スプリッターと同じ作り）。

## 承認負荷の設計（必須）
カオスなコーパスは判断点が数百になりうる。全件確認は人が破綻する。
- **高確信（lane=bulk）**: 重なりが高く（既定 min_overlap ≥ 0.8）かつタイトルが揃っている
  （平均ペア類似度 ≥ 0.5。**完全一致は要求しない**——実運用の重複はタイトルが表記揺れ
  しているのが普通で、一致要求だと bulk レーンがほぼ発火しないため）→ 「明白な重複
  N 組をまとめて統合します。一括承認?」で **1 操作**。
- **曖昧/矛盾（lane=individual）**: 上記未満、または事実衝突の疑い → **1 件ずつ**「これは判断が
  必要」とエスカレーション。
- 判定は確信度スコア（重なり率・タイトル一致など）で自動ルーティング（`classify_confidence`）。

## 安全性・冪等性（重要・厳守）
- **原典は破壊しない**: 「生ソースは別データセットで保持」（[architecture.md] のリスク対策）。
  統合で消すのは Wiki 上の重複ページのみ。退役は即削除でなく `status: deprecated` ＋
  統合先へのリンク（redirect 的）を既定とし、削除は別途承認。
- **draft で作る**: 統合ページも status: draft。人が GROWI で確認・公開してから検索に反映。
- **再実行で壊れない**: 既に統合済み（or 単独）のページは候補に挙がっても確信度で弾く／
  no-op。同名衝突は一括取り込み側の知見（[splitter-design.md](splitter-design.md)）と同様に扱う。
- **欠落ゼロが最優先**: 統合本文生成 LLM には「全ページの主張を保持、要約で落とさない」を厳命。
  統合直後に完全性チェック（`check_completeness`）を実行し、欠落の疑いがあれば統合先
  ページ本文冒頭に警告バナーを自動挿入する（実装済み。下記参照）。

## スコープと進捗
- ✅ `dify/dedup/`: 候補ペア → クラスタ化（union-find）→ 重なり統計（difflib）→ 確信度振り分け
  → 提案データ構造、を **純粋ロジック＋単体テスト**で実装（文書非依存・stdlib のみ）。
- ✅ **Dify 配線＝提示まで**（[dify/workflows/dedup-bot.yml](../dify/workflows/dedup-bot.yml)）。
  一覧取得 → 接頭辞フィルタ → 各本文取得(Iteration) → 提案組立(Code) → lane 別提示。
  **候補ペアは本文総当たり difflib で生成**（意味検索=Knowledge Retrieval は大規模化時に差し替え）。
- ✅ **④承認→⑤実行（統合→退役）を実装・実機検証済み**（`dify/dedup/execution.py` +
  `dify/dedup/tools/build_dedup_dsl.py` で DSL に execute 分岐を合成）:
  - 承認は**単一ターンの承認語**で判定（会話変数を使わない。実行ターンで再検出＝冪等）。
  - **高確信（lane=bulk）クラスタのみ自動統合**。要確認は提示のまま（人の個別判断）。
  - 各クラスタ: 統合LLM（事実保持・矛盾注記）→ 統合先(representative)を **draft で upsert** →
    重複元を **`POST /pages/deprecate`**（status:deprecated + 統合先リンク）。
  - **冪等**: 退役ページは検出から除外（status:deprecated をスキップ）。2 回目は 0 クラスタ。
  - ローカル Dify + 実 GROWI で検証（提示→統合→退役→sync除外→再実行0件）。完全 bot 経由でも動作。
- ✅ **完全性チェック（`check_completeness`）を DSL に組み込み・実機検証済み**。統合LLMの
  直後に完全性チェックノードを挟み、元ページの各行が統合本文に十分残っているか
  （difflib ベースの近似一致）を機械チェック。欠落の疑いがあれば統合先ページの
  frontmatter 直後に警告バナー（`⚠️ 完全性チェック警告`）を自動挿入する。
  **ハードなゲートにはせず**、最終判断は人が GROWI で公開前に行う（HITL の補助シグナル）。
  実機で欠落ケース（LLM が単文を箇条書きに再フォーマットし行単位比較でヒットしなかった
  ケース）を確認し、警告バナーが実際に GROWI 本文へ挿入されることを検証した。
  なお本チェックは行単位の近似一致であり、**意味的には欠落していない再フォーマット**
  （単文→箇条書き等）でも警告が出ることがある（偽陽性はあるが偽陰性より安全側）。
- ⬜ 要確認(individual)レーンの個別承認 UI、意味検索での候補生成（大規模化）。← 次ステップ。

> v1 の制約: Dify Code ノード配列出力 30 要素上限のため、対象を接頭辞でスコープして 30 ページ
> 以下にする前提。全社規模では一覧側のページング/分割か `CODE_MAX_*_ARRAY_LENGTH` 引き上げが要る。

## 提案データ構造（Code ノード出力）
```json
{
  "proposals": [
    {
      "cluster_id": 1,
      "page_ids": ["p3", "p7", "p12"],
      "titles": ["宿泊費を精算する", "宿泊費精算", "宿泊費の申請"],
      "representative_title": "宿泊費を精算する",
      "representative_path": "/manuals/総務/経費精算/_howto/宿泊費を精算する",
      "min_overlap": 0.84,
      "confidence": "high",
      "lane": "bulk"
    }
  ]
}
```
基準ページ（representative）は**最も情報量の多い（content 最長）ページ**を既定とする
（統合のベースにし、他ページの差分を溶け込ませる）。

## 検証方針
- コアは複数パターン（完全重複 / 近接 / 推移的クラスタ a-b,b-c / 無関係 / タイトル不一致）で
  単体テスト。文書種に依存しないこと。
- Dify 配線後は、わざと重複を含む複数文書を投入し、「高確信は一括・曖昧は個別」「統合で欠落
  なし」「原典退役が安全」を実機（ローカル Dify + GROWI）で確認する。
```
