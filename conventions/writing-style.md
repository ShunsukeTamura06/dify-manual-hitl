# ライティング規約

RAG で検索・回答されることを前提にした書き方の細則。
AWS の "Documentation best practices for RAG applications" 等の知見に基づく
（出典: [docs/research-notes.md](../docs/research-notes.md)）。

登録 Bot（LLM-1）の整形プロンプトにもこの規約を埋め込む。

---

## 構造

- **見出し・小見出しを階層的に使う**。文書構造が検索精度に直結する。
- **見出しの直下に 1〜2 文の要約を置く**。
  チャンクの意味的カバレッジが上がり、類似検索が当たりやすくなる。
- **大きな文書は小さく分割する**。1 ページに複数トピックを詰めない。

## リスト

- **番号付きリストは連番を厳守**。飛び番は LLM を混乱させる。
- **手順の項目間に接続表現を入れる**。
  例:「ステップ 2 が完了したら、次に…」。流れを LLM がたどれる。

## 表（現場の実態にあわせた方針）

現場のマニュアルは Excel 由来で表が多く、表は表のまま残す必要がある。
「表を避けてフラット化」は手間が大きく破壊的なので**採用しない**。

代わりに **表は残しつつ、検索用の平文を併記**する（両取り）。

- **表はそのまま残す**（人が見る用。GROWI で普通に描画される）。
- 表の**直前に、内容を要約した平文を 1〜数文置く**（検索ヒット用）。
  この平文は登録 Bot（LLM-1）が**自動生成**するので、書き手の手間は増えない。

  推奨形:
  ```
  ## 経費上限一覧
  交通費の上限は月 5 万円、宿泊費は 1 泊 1.5 万円、会議費は 1 回 2 万円です。

  | 科目 | 上限 |
  |------|------|
  | 交通費 | 月5万円 |
  | 宿泊費 | 1泊1.5万円 |
  | 会議費 | 1回2万円 |
  ```

  → 人は表を見る、RAG は平文を拾う。手間ゼロで両立する。

## 用語

- **略語・社内用語は必ず定義する**。LLM は社内文脈を知らない。
  初出で「経費精算システム（以下 KSS）」のように展開する。
- **表記を統一する**。同じ概念を「経費」「費用」「コスト」と揺らさない。
  揺れると別物として検索される。

## 冒頭の導入（session starter）

- ページ冒頭に、想定される問いへの入口文を置く。
  例:「ソフトウェアの発注手順を探しているなら、以下の通りです。」
  質問とのセマンティック一致が上がる。

## 画像

- 画像には**テキストの説明を併記**する（alt や本文で）。
  Vision 補助になり、画像が見られない環境でも情報が伝わる。
- 図・フローは可能なら **Mermaid** で書く（テキストなので検索・編集・差分に強い）。

  ```mermaid
  flowchart TD
    A[申請書作成] --> B{金額判定}
    B -->|10万円超| C[部長承認]
    B -->|10万円以下| D[課長承認]
  ```

## 一般

- **1 文を短く、曖昧さを減らす**。指示語（それ・これ）を多用しない。
- **能動態・具体的な主語**で書く。「承認される」より「上長が承認する」。
- 数値・固有名詞は正確に。出典が古い可能性があれば注記する。

## チェックリスト（公開前・軽め）

「誰も正解を完全には知らない」前提なので、公開前チェックは最小限でよい。
正しさは読込時の透明性（出典・更新日・矛盾検出）と継続フィードバックで担保する。

- [ ] 見出し直下に要約があるか
- [ ] 表の直前に検索用の平文があるか（登録 Bot が自動生成）
- [ ] 略語を定義したか
- [ ] 明らかな誤り・機密の混入がないか（ざっと目視）
